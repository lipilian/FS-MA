02 · Module responsibilities

The executable selects inputs and orders the work. The reusable library owns stereo processing and inference; the plugin provides the custom TensorRT operation.

Application entry points

app/

TSFS.cpp parses a capture directory and optional --measure, loads the engine, and calls rectification, inference, and fused full-image XYZ reconstruction in sequence. The reconstruction method waits for GPU completion before returning. It also reports failures and returns the process exit status.

desktop_main.cpp creates the Qt application and starts DesktopController, which starts calibration and opens an inference-loading splash after successful completion or explicit saved-calibration reuse; reconstruction opens only after both FS and SAM initialization succeed. Ordinary calibration close exits.

build_single_engine.cpp is a separate tool: it registers the GWC plugin, parses ONNX, and builds a serialized TensorRT engine.

Shared utilities

core/ · Logger

fs/core/Logger.hpp

Provides Logger::log() and Logger::error() for diagnostic output. The CLI and stereo module use it to report progress and errors.

This folder currently contains logging only. Camera frame/pair types live in capture/IStereoSource.hpp.

Images and camera geometry

stereo/ · StereoFrame

fs/stereo/StereoFrame.hpp

Accepts file paths or in-memory RGB images plus a StereoCalibration. Both constructors share validation and take independent copies of the images and calibration. rectify() runs stereo rectification, builds remap tables, and produces the rectified pair.

StereoCalibration.hpp declares the full raw intrinsics, distortion, rotation, and translation; from_file() reads the existing JSON schema. Callers can also populate these matrices directly. Memory input requires matching RGB CV_8UC3 images and float calibration matrices, with translation in metres.

StereoCameraParameters holds the rectified parameters: fx, fy, cx, cy, and baseline in metres. The class exposes the images and rectified camera parameters.

TensorRT inference

inference/ · FS

fs/inference/FS.hpp

Owns the TensorRT runtime, engine, execution context, CUDA stream, and reusable host/device buffers. Engine loading registers the GWC plugin before deserialization and preallocates the two 960×800 CPU RGB resize images alongside the existing GPU/pinned buffers.

Resizes RGB images to 800 high × 960 wide, packs FP32 NCHW inputs, and submits inference. It scales the rectified camera intrinsics to that grid and retains the baseline.

CUDA postprocessing · Fused XYZ reconstruction

inference/ · PostProcessing

fs/inference/PostProcessing.hpp

fs::postprocessing::compute_xyz_map() fuses disparity validity checks, depth clipping and XYZ projection in one kernel. Each thread handles one pixel; 800×960 uses 3000 blocks of 256 threads with a bounds check and no strided loop. The CUDA source is compiled into fs_core.

The launcher receives read-only disparity, a separate XYZ output, an optional selection mask, dimensions, model-grid intrinsics, baseline in metres, depth limits and the caller's stream. It allocates no buffers and returns asynchronously. Invalid pointers, dimensions, camera parameters or depth limits return cudaErrorInvalidValue.

FS::compute_xyz_map(float min_depth_m = 0.0F, float max_depth_m = 1.0F) uses model_camera_parameters_ and its existing stream. FS allocates and reuses xyz_map_device_: contiguous FP32 [800][960][3], interleaved X,Y,Z in metres (9,216,000 bytes). The original disparity_output_device_ remains unchanged; no extra filtered-disparity or validity-mask buffer is used.

The low-level launcher can accept a mask, but FS::compute_xyz_map() passes nullptr and always reconstructs the whole image. For finite positive disparity d and mandatory u ≥ d, compute Z = fx × baseline / d, X = (u − cx) × Z / fx, Y = (v − cy) × Z / fy. Keep only finite XYZ with Z > 0 and min_depth_m ≤ Z ≤ max_depth_m. Limits must be finite with 0 ≤ min_depth_m < max_depth_m; every rejected pixel writes all three components as zero. Validity is read from Z > 0.

Masked neighbourhood denoising: FS::denoise_xyz_map(0.01F, 3, 2) runs one 3×3 pass inside the mask on the FS stream after full-image XYZ. It counts valid neighbours within 0.01 m in 3D. A selected pixel with all eight neighbours selected requires three valid neighbours; boundary pixels require max(1, min(selected_neighbour_count, 2)). Unselected XYZ is copied unchanged to the separate output. Only selected neighbours contribute to denoising, so the rules inside the mask still match Python. The separate output prevents cascading removals within a pass. After synchronization, FS swaps xyz_map_device_ and xyz_scratch_device_; the current XYZ pointer therefore refers to the denoised output without a device-to-device copy. FS owns and allocates the additional GPU XYZ scratch buffer, GPU/pinned mask buffers and CPU mask resize buffer during splash loading, then reuses them. Disparity is unchanged.

Validation: 75 synthetic denoising cases matched the Python helper exactly, including image edges, holes, thin selections and an 800×960 grid. In a real capture, the selected region retained 110596 points before denoising and 110362 afterwards, matching Python inside the selection. The final result also preserves every XYZ value outside the selection. Real-engine and Qt checks verified nearest-neighbour resizing, buffer reuse, empty/full masks, unchanged unselected XYZ values, denoising toggle/distance and downstream invalidation.

The FS method synchronizes before returning and reports launch and execution errors. Depth limits may be changed and XYZ recomputed without another inference. Call order is the caller's responsibility: load engine, set model camera parameters, prepare images, infer, compute XYZ. No input/inference readiness flags are maintained. FS supports set_selection_mask(), which resizes a rectified-left byte mask with nearest-neighbour interpolation and uploads it to the model grid. An empty mask selects the full image for denoising; preparing a new stereo pair clears the previous selection. Qt supplies the confirmed mask for each reconstruction. CPU XYZ download and Jet display are implemented.

Interactive segmentation

inference/ · SamSegmenter

fs/inference/SamSegmenter.hpp

Owns the SAM 2.1 Hiera Large encoder and decoder, execution contexts, an independent non-blocking CUDA stream and reusable device/pinned buffers. The splash loads both engines and allocates buffers without dummy inference.

The first prompt calls setImage(): resize rectified-left RGB to 1024×1024, normalize and pack NCHW on the CPU, upload, then encode. Three feature maps stay on the GPU and are bound directly to the decoder. These are SAM features; they are not shared with FoundationStereo.

predict() scales full-resolution prompt coordinates to 1024×1024 and accepts 1–64 prompt entries: background 0, foreground 1, box corners 2 and 3. Mask input and its flag remain zero. Each edit uploads prompts, runs the decoder, downloads three 256×256 float masks and their scores, selects the highest score, resizes logits to the original image on CPU, then thresholds at zero. It returns an owned 0/255 mask.

A new frozen image clears the encoder cache. Prompt/image revisions in the controller and worker discard stale work and results. Brush strokes are CPU edits and do not invoke SAM. See the local ONNX paths and engine-build commands.

CPU geometry and display

geometry/ · MeshBuilder

fs/geometry/MeshBuilder.hpp

fs::build_constrained_mesh() consumes aligned CPU XYZ, mask and RGB, builds constrained image-plane triangles through the native Triangle C library and returns metric vertices, RGB, faces and area. Input matrices stay unchanged.

PipelineWorker::buildMeshCPU() adds calibrated camera display metadata and emits a shared immutable MeshResult. widgets/MeshView renders it in Qt OpenGL on the GUI thread. Mesh generation and export do not depend on Python or VTK. See the algorithm and hole policy.

Independent shared library

inference/plugins/ · GWC

GWCVolumePlugin.hpp/.cpp provide the TensorRT Plugin V3 implementation and registration entry points.

GWCVolumeKernel.hpp/.cu declare and implement the CUDA launcher for groupwise correlation. Both inference and engine building link the resulting libGWCVolumePlugin.so.

Registration includes a C entry point, fs_register_gwc_volume_plugin(), for dynamic loaders.

Camera acquisition · Optional SDK module

capture/ · SentechStereoSource

fs/capture/SentechStereoSource.hpp

Implements IStereoSource with separate workers for left 21LJ548 and right 21LJ530. Device roles match exact names or serials, never enumeration order.

Converts SDK images to owned RGB8 snapshots and returns a StereoCameraPair containing images, frame IDs, camera-local timestamps, and host arrival times. Each pair uses a new frame from both sides, with a configurable host-arrival skew limit.

These are independent continuous streams, not synchronized exposures. CalibrationWorker uses the source for preview and calibration samples, then hands it to PipelineWorker for live preview and frozen-pair reconstruction. Raw capture export is implemented in the fourth-step Save results panel.

Experiment and reference code

python/

fs_high_resolution_utils.py contains shared rectification, inference, disparity postprocessing, point-cloud export, constrained mesh construction, and area calculation helpers.

The PyTorch and TensorRT notebooks run experiments and write geometry results; export scripts prepare ONNX models. The C++ CLI does not call this Python pipeline.

C++ build setup

Install OpenCV 4 development files, including aruco (libopencv-contrib-dev on Ubuntu), Qt 6 Widgets (qt6-base-dev), CUDA and TensorRT development files. The recorded development environment uses CUDA 13.3 and TensorRT 11.2; CMake defaults to GPU architecture 120 and enables C, C++17 and CUDA17. The Sentech SDK defaults to /opt/sentech; override it with -DFS_SENTECH_ROOT=/path/to/sdk.

FS_BUILD_DESKTOP defaults to ON. Use -DFS_BUILD_DESKTOP=OFF for file-only builds without Qt or Sentech SDK dependencies. Existing CMake build directories retain their cached option values. The desktop requires Qt OpenGLWidgets for mesh display. Triangle 1.6 is built from the bundled C source; neither VTK nor a Python runtime is required.

For a fresh build directory on this workstation when CUDA is not on PATH, supply its location explicitly. Pass the compiler location when configuring a fresh directory; existing directories retain their own cached settings:

04 · CPU mesh · Triangle constrained Delaunay

geometry/MeshBuilder.hpp/.cpp implements fs::build_constrained_mesh() using native Triangle 1.6. It follows python/fs_tensorrt800x960_gwc_plugin.ipynb: all retained points on the 960 × 800 grid, with no interior downsampling.

  1. Split the selection into 8-connected components; retain selected finite XYZ with positive Z.
  2. Extract each component’s largest exterior contour, snap it to nearest retained image pixels and remove consecutive duplicates. Split repeated-vertex walks into nonzero-area cycles, discarding zero-area spurs; skip a component only if no valid cycle remains.
  3. Pass the image-plane UV vertices and exterior segments to Triangle using pzQ; the Python wrapper automatically adds z to its pQ call. Verify every constraint edge before filtering and reject inserted vertices without retained XYZ.
  4. Keep triangles whose rounded centroid belongs to the same mask component, whose longest 3D edge is at most 0.02 m, and whose Z spread is at most 0.01 m. Compact referenced vertices, retain RGB and sum triangle areas in double precision.

Holes: internal holes are not submitted as constraints. Nearby retained points may bridge denoising gaps or parts of mask holes if the centroid and 3D tests pass. Rejected triangles are not filled afterwards. Equal-distance contour snapping uses the lowest input index; SciPy may choose a different tied neighbour.

Memory and threads: FS inference → full-image XYZ → selected-region denoising stay on the FS CUDA stream. The existing depth-display download supplies an owned CPU XYZ map. PipelineWorker retains that allocation plus the CPU RGB and nearest-neighbour mask; buildMeshCPU() runs entirely on its QThread and does not call CUDA. A shared immutable result reaches the GUI thread, which uploads display vertices to an OpenGL buffer. No mesh GPU scratch is allocated during the splash. Triangle calls are serialized because its predicates use global state.

Camera display: Show camera is checked by default in the fourth tab. An amber frustum marks the rectified left optical centre (XYZ origin) and +Z viewing direction, using the reconstruction intrinsics. Its short drawn length is illustrative. Camera and mesh share the same display transform; rotation stays centred on the mesh bounding box. When shown, the view fits both; toggling preserves user rotation, pan, zoom and workflow completion.

GPU mesh framework: PipelineWorker::buildMeshGPU() receives an owned snapshot of the current confirmed mask. FS::prepare_gpu_mesh_inputs() checks XYZ readiness, uploads the mask with nearest-neighbour resizing on the existing FS stream, and returns a short-lived MeshGPUInputs view of the FS-owned XYZ, left RGB input tensor (FP32 NCHW, 0–255), mask, dimensions and stream. The XYZ pointer is obtained after any denoising buffer swap. The worker consumes the view immediately; it is never sent to the GUI or retained across FS mutations. geometry/MeshBuilderGPU.cu currently validates the inputs and returns MeshGPUStatus::NotImplemented. Its interface has no CPU RGB argument or CPU MeshResult output. The intended output is GPU buffers shared with OpenGL; buffer ownership and CUDA/OpenGL synchronization remain to be implemented. CPU mesh generation remains available; the GPU placeholder neither marks mesh completion nor replaces a valid CPU result. No new stream, XYZ upload/download or GPU mesh scratch is introduced.

Workflow: CPU mesh is available in the fourth tab after depth reconstruction. Geometry contains maximum edge and depth-jump settings. Changing either clears only the mesh; changing the input, mask, depth or denoising invalidates downstream results. View changes preserve completion. Cancellation is checked around triangulation and during filtering; it does not interrupt Triangle mid-call.

Saving: the fourth step has a Save results sidebar with independent choices for raw left.png/right.png, calibration JSON under its original filename, mask.png and mesh.ply. Browse selects an output folder; Save selected writes only checked items on the pipeline QThread. Save all exports all five files regardless of the checkboxes and is enabled only when all results are current and an output folder is selected. The mask is the full-resolution confirmed binary raster in rectified-left coordinates. PLY is binary little-endian, with original XYZ in metres, RGB bytes and triangle indices; it excludes camera markers and display transforms. Imported calibration JSON is snapshotted with the frozen pair. Live/confirmed calibration is serialized from the handed-off in-memory session and keeps the original basename, even if its source file has disappeared. Existing selected files require overwrite confirmation. All files are staged before individual atomic commits; saved paths and failures are logged. A stale mesh cannot be saved, and saving does not alter workflow completion.

Timing: the worker logs input preparation, synchronized inference, post processing (XYZ/denoising and download/depth-image preparation), and CPU mesh build separately in milliseconds with three decimal places. These are wall-clock measurements through completed work, excluding GUI rendering.

Validation: a fixed real XYZ/mask fixture produces 110,359 vertices and 218,294 triangles, with identical vertices and face connectivity to Python and area 0.0786497924673 m². Native CPU generation took about 0.13 s on this machine (one observation). Synthetic cases cover concavity, internal gaps, multiple components, empty results, cancellation and unchanged source XYZ. Qt workflow and OpenGL rendering are checked separately.

Triangle’s original notices are retained in cpp/third_party/triangle; see SOURCE.md for provenance and redistribution terms. Triangle documentation.

05 · Runtime flow

The desktop uses a background pipeline worker for computation. The main thread handles interaction and display; the two CUDA streams belong to FS and SAM respectively.

  1. Calibrate or reuse a saved calibration

    CalibrationWorker detects the board, captures samples, solves and saves. Finish uses the solve quality gate; Check new pose is optional. A valid saved session can be explicitly reused. The source, confirmed calibration and exposure transfer after calibration work stops.

  2. Initialize during the splash

    PipelineWorker creates FS and SamSegmenter, loads three TensorRT engines and allocates their reusable resources. Open reconstruction only after both models are ready. No mesh scratch allocation or dummy inference is required.

  3. Import or capture a raw pair

    Check the required files or freeze a fresh camera pair. StereoFrame performs CPU rectification and retains raw and rectified images. Only successful preparation replaces the frozen input and clears downstream caches.

  4. Draw and confirm the region

    SAM box/point prompts use the frozen rectified left image. Manual Brush/Eraser corrections remain on CPU. Finish draw confirms a full-resolution binary mask and opens Depth map.

  5. Reconstruct on the FS stream

    Scale intrinsics; resize and upload RGB inputs and the mask; synchronize uploads. Run inference, full-image XYZ and optional mask-only denoising. Each timed stage waits for completed work. No application-issued XYZ or disparity download occurs between inference and denoising.

  6. Download once and prepare depth

    Download current XYZ to an owned CPU matrix. Extract final Z, apply the fixed-range Jet palette and make invalid pixels black. Independently resize rectified-left RGB to the same 960-wide × 800-high grid. Retain CPU XYZ, RGB and mask for mesh generation; emit copied QImages to Qt.

  7. Generate and inspect the mesh

    Next opens 3D browser after depth is current. CPU mesh calls native Triangle on the pipeline QThread using the retained CPU arrays. MeshView uploads display geometry through its OpenGL context; its camera marker and display transforms do not change metric mesh data.

  8. Save selected results or all results

    Choose a folder in the fourth-step sidebar. The worker encodes raw PNGs, calibration JSON, confirmed mask and/or PLY from current CPU snapshots, with no new inference or XYZ download.

CLI scope: TSFS <capture-directory> [--measure] still requires left.png, right.png, calibration.json and the fixed FS engine path. It rectifies, prepares inputs, runs inference (or ten GPU-event-timed runs), then computes full-image XYZ on GPU. It does not run SAM, denoising, CPU download, meshing or export. The desktop's alternate calibration filename discovery does not change the CLI.

In-memory stereo input · API and ownership

Public headers use the cpp/include root, for example fs/inference/FS.hpp and fs/stereo/StereoFrame.hpp. The file-path constructor loads RGB images and calibration, then delegates to the same validated memory constructor:

#include "fs/stereo/StereoFrame.hpp"

// left_rgb and right_rgb are matching CV_8UC3 RGB images.
StereoCalibration calibration = StereoCalibration::from_file("calibration.json");
StereoFrame frame(left_rgb, right_rgb, calibration);
frame.rectify();

// Use frame.rectified_left(), frame.rectified_right(),
// and frame.rectified_camera_parameters() for inference.

Fully in-memory callers can populate the six StereoCalibration fields directly: left_camera_matrix, right_camera_matrix, left_distortion, right_distortion, right_to_left_rotation and right_to_left_translation.

  • Images must be non-empty, equal-size 2D RGB CV_8UC3. Non-contiguous ROIs are supported. Convert BGR sources to RGB first; the Sentech source already provides RGB.
  • Matrices must be finite, single-channel CV_32F or CV_64F. Intrinsics are 3×3 with positive focal lengths and last row [0, 0, 1]. Distortion is a row/column vector containing 4, 5, 8, 12 or 14 coefficients; use explicit zeros for no distortion.
  • Rotation must be a proper 3×3 rotation. Translation is a nonzero three-element row/column vector in metres. Calibration must match the input image grid.
  • Legacy right_to_left_* field names are preserved. The calibration solver stores OpenCV’s left-to-right transform; these values pass unchanged to stereoRectify, without inversion or unit conversion.
  • StereoFrame deep-copies both images and every matrix, storing calibration as CV_64F. Callers may reuse or release their buffers after construction. Invalid input throws std::invalid_argument; missing or unreadable calibration files also raise exceptions. from_file() reads the required matrices; the frame constructor validates their shapes and values.

06 · Current boundaries and validation

Implemented

Calibration handoff and splash initialization, strict folder import, camera/frozen preview, interactive SAM and manual mask editing, four-step completion tracking, GPU XYZ and masked denoising, Jet display, CPU Triangle mesh, OpenGL camera/wireframe controls and selected/all result export are connected in the desktop.

Recorded validation includes Release builds, real-engine runs, CUDA/Python comparisons, SAM/ONNX comparisons, CPU mesh fixtures and temporary Qt workflow checks. These historical checks are not a permanent test suite or a hardware acceptance guarantee.

The latest save/import checks verified exact raw pixels, calibration snapshots, confirmed mask and binary PLY contents; Save all with every checkbox cleared; overwrite refusal; stale-mesh rejection; missing-file combinations in both calibration modes; alternate JSON names; and preservation of the old input after an import error.

Remaining boundaries

The public FS API downloads XYZ, but has no raw disparity download accessor. Folder import restores raw images and calibration only; it does not reload mask.png or mesh.ply into later steps. Reports and additional session metadata are not implemented.

Physical-camera handoff/unplug recovery, preview rate, real-board accuracy and long-session memory stability still need acceptance on the device. Camera streams do not provide synchronized exposure. CPU triangulation is cancellable around its native call, not inside that call.

See the current implementation notes and the algorithm overview. The source and this guide describe current behavior; older benchmark sections in the development notes retain their historical scope.

Sentech source settings and SDK behaviour

The current implementation is cpp/src/capture/SentechStereoSource.cpp, with pairing and identity helpers in StereoCaptureSupport.hpp. The Qt window binds left STC-MCS500U3V(21LJ548) and right STC-MCS500U3V(21LJ530). The source API also accepts exact user-defined names or serials; missing, ambiguous or same-camera matches fail.

Requested timed exposure defaults to 100,000 µs (100 ms) and is adjusted to the camera’s supported increments. Edit it before connecting; the input is disabled while connected. Continuous automatic white balance is requested when supported. Each camera has its own acquisition worker and produces owned RGB8 snapshots; camera settings are not saved to device user sets.

SentechStereoOptions::max_arrival_skew defaults to 100 ms. Host arrival includes transport latency, while device timestamps belong to independent camera clocks. Keep the board still during capture. Capture errors propagate to the Qt worker, and acquisition threads join before SDK buffers/devices are released.

The library links StApi TL/IP, GenICam, the SDK’s turbojpeg and OpenCV core. It supplies SDK runtime search paths and sets GENICAM_GENTL64_PATH only when absent.

InferenceSplashWindow displays initialization status, elapsed time and cancellation. On failure it offers engine-file selection and retry. ReconstructionWindow owns collapsible input/calibration details and depth controls, sequential stereo, region, depth and 3D tabs, the Mask draw sidebar and logs. Right-side tab indicators show green completed checks or yellow pending dots. Toolbar actions follow the current tab: Capture pair for stereo, Finish draw for region, Reconstruct and Next for depth, CPU mesh and GPU mesh for 3D. 10 · Threads and ownership

A QThread executes CPU code; a CUDA stream orders GPU work. They are different resources.
OwnerWork and lifetime
Qt main threadDesktopController, windows, controls, MaskEditor CPU raster editing, QImage presentation and MeshView OpenGL rendering. It submits operations and receives queued state/result signals.
CalibrationController / CalibrationWorkerDedicated calibration QThread: camera polling, board detection, solve, check, JSON load/save and session handoff. It finishes before the reconstruction worker takes over the source.
PipelineController / PipelineWorkerA single dedicated QThread serializes model loading, rectification, FS and SAM calls, CPU Jet preparation, Triangle meshing and file encoding. It owns the active source, frozen StereoFrame, FS, SamSegmenter, calibration snapshot and cached CPU mesh inputs.
FS CUDA streamFS owns input uploads, TensorRT enqueue, full-image XYZ, selected-region denoising and XYZ download on this stream. The stream and reusable buffers live with FS.
SamSegmenter CUDA streamSeparate non-blocking stream for image/prompt upload, encoder, decoder and mask/score download. The pipeline QThread calls both models serially; separate CUDA streams do not imply simultaneous UI jobs.
Sentech acquisition workersOne capture worker per camera supplies owned RGB snapshots to the active Qt worker. These are separate from both Qt worker threads and CUDA streams.

PipelineController gates ordinary actions with busy state and an atomic cancellation flag. SAM requests also carry prompt revisions and image IDs. PipelineWorker catches action errors and publishes status/log messages; stale SAM results are discarded. Closing requests cancellation and waits for camera/model cleanup. GPU waits occur on the worker, not on the Qt main thread; running CUDA work and Triangle calls stop only at their safe boundaries.

11 · CPU / GPU memory flow

The FS model grid is 800 rows × 960 columns, or 960 pixels wide × 800 high. XYZ is FP32, interleaved X/Y/Z in metres, in the rectified left camera frame (+X right, +Y down, +Z forward).

From FS inference through denoising, application code uses the FS stream and issues no intermediate disparity/XYZ D→H transfer. There are synchronization points between stages; synchronization itself is not a memory copy. SAM has its own earlier mask/score downloads. OpenGL display uploads are a later, separate operation.

Splash allocations versus per-result allocations

FS loads the TensorRT engine/context, binds GPU input/output buffers, and allocates XYZ, denoising scratch, GPU/pinned mask storage, pinned RGB-input staging and model-size CPU RGB/mask matrices during splash initialization. SAM allocates its contexts, GPU image/features/prompts/masks/scores, required pinned staging and 1024×1024 CPU resize matrix there too. First-image encoding still waits for an actual image and prompt.

CPU XYZ downloads, Jet intermediates, copied QImages, mesh vectors and file-encoding storage are created later as results are produced. The worker retains the owned XYZ download through cv::Mat reference counting for CPU mesh; it does not download the same XYZ again. Changing only mesh thresholds can reuse those CPU inputs.

SAM feature reuse

The encoder retains [1,32,256,256], [1,64,128,128] and [1,256,64,64] FP32 feature maps on its GPU stream. Same-image prompts rerun only the decoder. Three float masks and scores return to pinned CPU staging for best-score selection and full-resolution interpolation before thresholding. Manual edits remain CPU raster overrides; they are not fed back through decoder mask_input. FS and SAM do not share encoder features.

12 · Capture loading and result saving

Required capture files

Import capture opens a folder chooser. PipelineWorker requires left.png, right.png and a calibration JSON even when Use capture calibration is unchecked. It reports all missing filenames together in status and log; directories do not count as files. Empty or unreadable files also fail. With capture calibration selected, StereoFrame loads and validates its matrices and images; any available calibration image-size metadata must match.

Calibration lookup tries calibration.json, then sentech_stereo_calibration.json, then the current confirmed calibration basename. The first existing file wins; an invalid preferred file produces an error rather than silently selecting another. With Use capture calibration unchecked, the required folder JSON is checked for presence/readability, but the actual matrices come from the confirmed in-memory session and the raw images must match its grid.

Only successful rectification replaces the frozen pair and associated calibration snapshot. An import failure keeps the previous valid input. Imported mask.png and mesh.ply are currently ignored; loading starts a new mask/reconstruction workflow.

Existing output names prompt for replacement before submission. The worker checks destinations and filename conflicts, stages every selected file with QSaveFile, then commits each file atomically. This is per-file atomic replacement, not a transaction spanning the whole set; if a later commit fails, earlier saved paths remain in the log. Saving logs paths and elapsed time without changing step completion.
